## Learned

- **The decoupling worked, verified two ways** (`self_checked, high confidence`): the usual 12/12
  cross-radius pre-freeze-parity checks stayed `identical: true` (same mechanism as 2026-08-23 —
  `setPartnerViewRadius` can't fire before `FREEZE_STEP` either), *and* — new and more direct —
  `postFreezeLandmarkVisibleCount` came back **exactly identical across all three radii, for every
  seed** (seed 1001: 0/38 at radius 2/4/6; seed 1002: 19/38 at all three; seed 1003: 0/38 at all
  three). The landmark gate itself never moved by construction, but this also rules out the
  *indirect* channel that stayed open in principle (post-freeze action divergence shifting the
  frozen agent's own position near landmarks) — at least for these three seeds and this grid size;
  n=3 doesn't establish it's silent in general.
- **The landmark confound was actually contributing to the non-monotonicity** (`self_checked,
  medium confidence`): with it closed, mean `|diffMean|` now moves 0.0324 → 0.1849 → 0.1892 across
  radius 2/4/6 — rising and roughly plateauing, not dipping. 2026-08-23's confounded-landmark run
  had a real drop over the same interval (0.1799 → 0.1514). That specific dip doesn't reproduce
  once landmarks are held fixed, which weakens (doesn't eliminate) attributing all of 2026-08-23's
  non-monotonicity to pure `n=3` sampling noise — some of it looks landmark-driven instead.
  Per-seed detail is still large and inconsistent in sign: seed 1003 goes `0.0000` → `+0.4271` →
  `-0.5103`, its largest-magnitude swing across any sweep so far.
- **Seed 1001's `diffMean` is identical at radius 4 and 6 again** (`self_checked, high
  confidence`), `-0.013825112267544395` bit-for-bit — same explanation as 2026-08-23 (its
  partner-visible tally already reached 38/38 at radius 4, so `relativeEntry`'s partner output
  can't change at radius 6), now confirmed on the correct partner-only tally instead of the
  confounded whole-`viewRadius` one.
- **What this run does and doesn't settle**: it rules out landmark-gate confounding as an
  explanation for the non-monotonicity, and the closed-confound trend is now closer to monotonic.
  It does *not* resolve whether the remaining per-seed swings are a real mechanism or `n=3`
  sampling noise — that still needs independent seeds, not another radius-axis rerun at the same
  three, per the PR #50 review's own "Next" line ("not more seeds yet [...] and if decoupling
  flattens the non-monotonicity, that's worth more than another n would have told you" — it
  flattened partially, which the review anticipated as informative either way).

## Assumptions made (proceeding unless told otherwise)

- Kept `setViewRadius()` (2026-08-23) as-is rather than reimplementing it in terms of
  `setPartnerViewRadius()`/a hypothetical `setLandmarkViewRadius()` — it still moves both gates
  together by construction (it sets `config.viewRadius`, which both the landmark loop and the
  partner fallback read), which matches its own doc comment and existing test
  (`test/env/gridworld.test.ts`'s "setViewRadius: takes effect on the next step..." case) unchanged.
  The two methods are independent knobs on the same class, not one layered on the other; adding a
  third `setLandmarkViewRadius()` for symmetry wasn't needed since no run wants to move the
  landmark gate alone.
- `postFreezeLandmarkVisibleCount`'s "any landmark visible" union (rather than a per-landmark
  breakdown, e.g. an array of `numLandmarks` counts) mirrors `postFreezePartnerVisibleCount`'s own
  single-boolean-per-step convention exactly, per the review's "landmark analogue" phrasing. A
  per-landmark breakdown would be a different, finer-grained metric — not built this run since the
  review didn't ask for one and the aggregate already answered the confound question (identical
  across radii per seed).
- Fixed the PR #50 body's "9/9" claim only in the proposal doc (dated correction), since a merged
  PR's own body can't be edited after the fact — flagging this explicitly rather than silently
  treating the doc fix as if it covered both.
