## Learned

- **`tf.variableGrads(f, varList)` wraps `f` in its own internal `tf.tidy` (`Engine.gradients`:
  `this.tidy('forward', f)`) and disposes everything `f` created except its returned scalar the
  moment `f` returns — before the caller regains control.** `self_checked, high confidence` —
  reproduced directly. First `WorldModel.step()` draft captured the next `RSSMState` tensors via
  outer-scope variables set inside the differentiated `forward()` closure, then called
  `tf.keep()` on them *after* `tf.variableGrads(forward, vars)` returned. That crashed on the
  *second* `step()` call (`Cannot read properties of undefined (reading 'backend')` inside
  `Engine.moveData`, triggered by `RSSMCell.step()`'s `tf.concat` trying to read the previous
  step's already-disposed `stochastic` tensor) — not the first, since the first call's forward
  pass still succeeds and returns a value; only reusing the (already-silently-disposed) captured
  state on the next call breaks. Root cause, confirmed by reading `tf-core.node.js`'s
  `Engine.prototype.gradients`: `variableGrads` runs `f` inside `this.tidy('forward', f)`
  specifically so intermediates *besides* `f`'s returned scalar don't leak — it has no way to know
  the caller wants to keep two *other* tensors `f` happened to create. Fix: call `tf.keep()` on
  those tensors *from inside* `forward()`, before it returns, not from the caller after
  `variableGrads` returns. This matters beyond this one file — any future code that needs
  `tf.variableGrads` to hand back more than just the loss scalar (e.g. any other recurrent-state
  training step) will hit the same trap if it tries to smuggle extra tensors out via closure
  capture read after the call. Worth a project-wide note if a second call site ever needs this
  pattern; not generalized into a shared helper here since `WorldModel` is still the only caller.
- Confirmed (via a warm-run `tf.memory()` leak check) that `tf.train.adam()` lazily allocates two
  persistent `tf.Variable`s (moment + velocity) per trainable weight on its *first*
  `applyGradients()` call, not at `tf.train.adam()` construction — a naive before/after tensor
  count taken across a model's *first* training step over-counts this one-time allocation as a
  leak. `self_checked, high confidence` — an early version of the leak test measured before any
  training step and found 12 "leaked" tensors that were exactly `2 * trainableWeights().length`;
  moving the baseline measurement to after 3 warm-up steps (so Adam's lazy vars already exist)
  brought net growth to exactly 0 across 20 further mixed train/eval steps.
