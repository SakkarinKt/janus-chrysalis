- **Root-caused the flakiness. It is not finite-difference tolerance noise.** With fixed

  `step()`+`.prior()` differentiation across ≥2 timesteps has a real, deterministic gradient error
  that grows with chain length: clean at 1 step (max error `0.00003`), then `0.0035` → `0.0069` →
  `0.0109` at 2/3/4 chained steps (epsilon `1e-4`). Confirmed non-vanishing across an epsilon sweep
  from `1e-2` down to `1e-6` — a true finite-difference truncation artifact shrinks toward zero as
  epsilon shrinks; this one is flat (even growing) across four orders of magnitude, which is the
  standard signature of a real analytic-gradient bug, not a tolerance problem.
- **Isolated the cause**: `straightThroughEstimator`'s `tf.customGrad`, but only in combination with
  the GRU cell's own repeated, shared-variable, `tidy()`-wrapped `call()`. Removing either
  ingredient independently makes the error vanish: (a) feeding back plain softmax `probs` instead of
  the STE sample (same chained `cell.call()`, no `tf.customGrad`) drops the error to float32-noise
  level at every chain length; (b) a minimal repro chaining `tf.customGrad` alone with no GRU cell
  involved shows no error at any chain length either. Only the combination — `tf.customGrad`'s
  output feeding into a later `cell.call()` invocation, repeated across timesteps sharing the same
  variables, inside one `tf.variableGrads` trace — reproduces it. Ruled out tensor-identity aliasing
  as the mechanism (a fresh `hard` tensor object per timestep changes nothing).

## Learned

- **[high, self_checked, execution-confirmed]** `RSSMCell`'s chained `step()`+`.prior()` gradient,
  as differentiated via `tf.variableGrads`, is wrong for chain length ≥2 — a real, deterministic bug
  that grows with chain depth, not finite-difference imprecision. Confirmed via epsilon-invariance
  (error doesn't shrink from `1e-2` to `1e-6`) and via a fixed-weight, always-reproducing repro.
- **[high, self_checked, execution-confirmed]** The 2026-07-22 validation (PR #22, notes §9) that
  this chain-length case "matches finite differences... across up to 4 chained steps" passed by
  chance: unseeded random weight init, only 3 of 9 bias elements checked, ~80% pass rate observed
  when re-run repeatedly. It read as "fixed" because it usually didn't trip the check, not because
  the underlying computation is correct.
- **[medium, self_checked]** The bug requires *both* `tf.customGrad` (the straight-through
  estimator) *and* the GRU cell's own repeated `tidy()`-wrapped `call()` in the same differentiation
  trace with shared variables — neither alone reproduces it. The likely internal mechanism (some
  interaction between `tf.customGrad`'s `save()`/`gradFunc` tape bookkeeping and `tidy()`'s
  scope-based tensor lifecycle when both nest in a loop) wasn't confirmed by reading `tfjs-core`
  internals — that's a bigger investigation than this run's scope, flagged for whoever picks up the
  fix.
- **[medium, self_checked]** This is a second instance (after the crash §8/§9 documented) of the
  same underlying pattern: tfjs's RNN/gradient machinery not being built for cells that get called
  repeatedly, sharing variables, within one differentiation trace — this time silently, not with a
  crash. Worth treating as a class of risk for this stack, not a one-off.
