- **Root-caused the flakiness — corrected mid-review.** My first pass (pushed as the initial version

  grew with chain length and re-tripped ADR-0002 decision 5. **@SakkarinKt's PR #26 review caught
  that this was wrong**, and after independently verifying every specific claim in the review
  (below), I agree: it's the straight-through estimator's known, by-design forward/backward
  mismatch, not a bug. ADR-0002 decision 5 stays closed; priority 3 is not blocked.
- **The actual mechanism**: `straightThroughEstimator`'s forward pass is defined to return exactly
  the fixed `hard` sample, unconditionally — so once its output feeds back as `z_{t-1}` into the next
  timestep, that path has zero numerical dependence on any upstream weight. Verified directly:
  bumping the GRU cell's bias by `0.5` leaves the fed-back sample bit-for-bit unchanged. Finite
  differences correctly see zero sensitivity through that path; the STE's backward pass still
  injects its intentional proxy gradient (the softmax Jacobian) through it anyway, because that's
  what a straight-through estimator is *for*. The "mismatch" — growing with chain length, and
  non-vanishing across an epsilon sweep from `1e-2` to `1e-6`, which is what first made it look like
  a real bug rather than tolerance noise — is exactly that injected gradient, not a discrepancy
  between two measurements of the same quantity.
- **Decisive verification** (fixed weights, epsilon `1e-4`): built the identical recurrence but with
  the STE-sampled feedback replaced by a literal constant equal to `priorHard` (`prior()` still
  called each step, so its forward pass is exercised the same way — only what feeds the *next* state
  differs). Loss values are identical to the real STE-forward at every chain length tried, and this
  detached version's gradient matches finite differences cleanly (`≤0.0005` at chain lengths 1–4).
  `|analytic_STE − analytic_detached|` (`0.0036 → 0.0071 → 0.0104` at chain lengths 2/3/4) matches the
  STE-forward's finite-difference "error" (`0.0035 → 0.0069 → 0.0109`) almost exactly — the whole
  discrepancy is the injected proxy gradient.
- **My original "isolation" experiments were confounded**, per the review: the probs-only variant
  "fixed" the mismatch only because it has no STE in it at all — nothing to disagree about. The
  minimal customGrad-only repro that showed no error at any chain length was a degenerate special
  case (`loss = sum(x)` makes the STE backward formula's `(dy − ⟨dy, softmax⟩)` term vanish
  identically for *any* chain length, including 1, because `dy` is uniform across the class
  dimension) — not evidence that chaining or the GRU cell was required. Reweighting that same minimal
  repro's loss to `[1, 2, 3]` (still chain length 1, still no GRU anywhere) reproduces a `0.36`
  mismatch, confirming the effect was never about chaining.

## Learned

- **[high, self_checked, execution-confirmed]** `RSSMCell`'s chained `step()`+`.prior()` gradient is
  correct — the ≥2-timestep flakiness was a test-scope gap (the STE forward/backward trap already
  documented for `priorDense` at chain length 1 also applies to the GRU cell's own weights once
  chaining routes them through the STE), not a computation defect. §9's 2026-07-22 "kill criterion
  did not fire" conclusion stands.
- **[high, self_checked, execution-confirmed]** A biased/proxy gradient estimator (straight-through,
  here) will show a persistent, epsilon-invariant mismatch against naive finite-differencing whenever
  its forward pass is held fixed/constant — that non-vanishing-across-epsilon signature, which is
  normally good evidence of a *real* bug (ruling out truncation/rounding noise), is not sufficient
  evidence on its own when a custom gradient is deliberately biased by design. Worth remembering
  before reading "doesn't shrink with epsilon" as proof of a bug anywhere else `tf.customGrad` shows
  up in this codebase.
- **[high, self_checked]** A degenerate loss shape (here: `sum(x)`, making the downstream gradient
  uniform across the categorical axis) can make an otherwise-real effect vanish in a "minimal repro,"
  making the repro's negative result misleading rather than clarifying. Worth choosing non-degenerate
  loss weightings by default in future isolation experiments on this codebase.
- **[medium, self_checked]** This project's "root-cause with rigorous, reproducible experiments"
  standard worked as intended even though my first conclusion was wrong: because every claim was
  backed by a checked-in, re-runnable script rather than prose alone, the reviewer (and I, re-
  verifying independently before touching anything) could check each specific number rather than
  re-litigate the whole investigation from scratch. The correction took one review round, not several.
